# OJGuard 3～5 分钟演示脚本

## 演示目标

让评审在最短时间内看到三件事：多 Agent 有真实分工、关键结论有确定性证据、自动修复
不能绕过人工审批。最终录制使用 `OJGUARD-DEMO-002` 的 AgentTeams Element 原始协作轨迹。

## 录制前准备

- Docker Desktop、后端、MCP、前端和 AgentTeams 全部健康；
- 浏览器预先打开 OJGuard 总览与 Element 对应房间；
- 数据库保留一个已完成样例，同时准备一个全新的 Demo 运行；
- 关闭通知、隐藏 `.env`、终端历史、账号邮箱和无关浏览器标签；
- 先演练一次，确认整段不超过 5 分钟。

## 镜头顺序与讲解

### 0:00～0:25：问题与结论

画面：OJGuard 总览。

讲解：传统题包工具擅长格式、编译和已有测试，却很难跨题面、Validator、标程、测试与
Checker 找到语义缺陷。OJGuard 让 Agent 提出可证伪风险，再由沙箱程序验证；没有证据
的判断不能成为已确认缺陷。

### 0:25～0:55：真实多 Agent 协作

画面：架构页快速展示五个 Agent，然后切到 Element 原始房间。

讲解：Judge Manager 将任务拆给规格审计、程序分析、对抗测试和 Checker 审计四个
Worker。指出一条任务分派、一条 Worker 回复和一条证据完整性复核消息，并展示对应的
Evidence ID。最后展示 4/4 回复和 Leader 的 `OJGUARD_DEMO_COMPLETE` 汇总。不要只停留在架构图。

### 0:55～1:55：执行主演示

画面：主演示页，点击“开始真实审计”。

讲解：Runner 使用 C++17 Docker 沙箱执行四类探针，默认断网并限制资源。结果应显示：

1. 大数输入导致标准程序整数溢出；
2. 题面允许的边界被 Validator 拒绝；
3. 负数反例淘汰错误正数求和程序，但原测试未覆盖；
4. Checker 错误接受正确答案后的多余 Token。

强调这四项都来自真实编译和执行，不是预写的模型回答。

### 1:55～2:35：Finding 与证据重放

画面：运行详情 → Evidence，打开整数溢出证据。

讲解：每条 Finding 关联 Evidence ID，证据保存输入、输出、退出码、工具版本、路径和
SHA-256。界面显示哈希验证结果。再打开 Agent Trace，说明同一 `run_id` 串联任务、工具、
证据和发布门禁。

### 2:35～3:35：双审批修复闭环

画面：候选补丁 → 审批中心。

讲解：Agent 只能产生 Diff。第一次批准才会写入隔离工作副本；随后运行原测试、新回归、
Oracle、错误程序和 Checker 攻击五项回归。全部通过仍不能发布，必须二次确认。完成后
显示 `READY_FOR_RELEASE`，同时说明系统没有连接真实 OJ，原题包始终不变。

### 3:35～4:10：基准与边界

画面：基准评测页。

讲解：10 个原创题包包含 8 个缺陷样例和 2 个干净对照。当前确定性基线为 8 TP、0 FP、
100% Recall、0% 干净题包误阻断，且 LLM 调用为 0。明确这只是规则基线，不冒充 AgentTeams
或模型质量结果。

### 4:10～4:35：安全与复用

画面：架构页或设置页。

讲解：七个 Skill 与八个 MCP 工具可供不同 Agent、CI 或外部适配器复用；AgentTeams 使用
K8s 后端且不挂载宿主 Docker Socket。本轮 DeepSeek 保守成本上限约 1.70 元，仍保留
6 元提醒、8 元停止保护；RAG 在 8010 预留但初赛明确关闭。

### 4:35～4:55：收束

画面：总览或报告。

讲解：OJGuard 的价值不是“让模型宣布程序正确”，而是让每个发布判断都能回到原始协作
消息、确定性执行记录和可重放证据。

## 故障备用方案

- Docker 首次编译慢：先展示已完成运行，再在后台启动新运行；
- AgentTeams 暂时无响应：展示真实历史房间和共享文件，不剪接成假实时过程；
- 前端接口失败：切换到已生成的 HTML 报告，并说明错误状态，不将失败描述为通过；
- DeepSeek 限流或余额不足：使用已缓存结果，明确模型调用状态；核心确定性验证不依赖模型；
- 时间超出：优先保留 AgentTeams 原始轨迹、四类真实缺陷和双审批，缩短基准介绍。
