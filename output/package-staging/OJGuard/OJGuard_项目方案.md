# OJGuard 项目方案

> 面向大规模在线编程测评的多智能体事故响应与可信重评平台
>
> 文档日期：2026 年 8 月 2 日

---

## 一、项目定义

### 1.1 项目名称

**项目名称：** OJGuard  
**参赛标题：** OJGuard——在线测评事故响应与可信重评
**英文名称：** OJGuard: Multi-Agent Incident Response and Trusted Rejudging for Online Judges

代码仓库、界面、报告、方案和演示统一使用 **OJGuard**。题包审计、Checker 验证、沙箱执行和发布门禁作为事故调查与结果验证所调用的基础能力。

### 1.2 一句话定位

> 当企业招聘考试、开发者认证或大型在线编程测评发生评测异常时，OJGuard 聚合异常信号，验证技术根因，计算受影响范围，生成处置与重评方案，并在人工审批后执行受控重评、核验成绩变化和沉淀完整证据。

### 1.3 核心原则

> **Agent 负责理解、规划和提出假设；确定性工具负责统计、实验、重评和核验；高风险业务结果由人类审批。**

任何严重结论必须附带查询结果、对照实验、沙箱执行、重评记录或完整性校验。没有确定性证据的判断只能保留为假设或转交人工复核。

### 1.4 为什么属于企业级复杂任务

OJGuard 处理的不是一次代码问答，而是横跨监控、评测、题库、成绩、招聘和客服系统的长周期事故：

- 输入来自指标、日志、提交记录、镜像变更、题包版本和投诉；
- 根因可能位于运行镜像、评测节点、配置、队列、题包或 Checker；
- 需要计算候选人、提交、成绩、排名和晋级影响；
- 批量重评可能制造二次故障，必须灰度、限流、暂停和回滚；
- 成绩写回、冻结排名和通知候选人需要独立审批；
- 事故关闭不能只看服务恢复，还要验证重评覆盖率和成绩一致性。

企业级复杂度来自真实业务依赖、角色制衡和结果验证，不依靠增加 Agent 数量或堆叠云产品制造复杂感。

## 二、业务问题、用户与价值

### 2.1 问题背景

一场企业校招编程考试可能同时服务数千名候选人，涉及评测节点、语言运行镜像、任务队列、题包、Checker、成绩系统、招聘批次和客服工单。镜像性能回归、节点退化、题包版本不一致或 Checker 缺陷都可能改变候选人成绩和晋级结果。

传统处理通常需要运维、题目、招聘和客服团队跨系统手工排查，存在以下困难：

- 告警、异常提交和投诉难以归并为同一事故；
- 相关性容易被误判为因果关系；
- 受影响候选人和提交范围难以准确计算；
- 一键全量重评可能冲击系统或引入新的不一致；
- 技术修复后缺少成绩与排名层面的独立核验；
- 审批、执行和通知记录分散，难以复盘与审计。

### 2.2 目标用户

- 企业招聘测评平台的技术和招聘团队；
- 在线编程教育与开发者认证平台；
- 高校大规模程序设计课程和在线考试平台；
- 算法竞赛与在线评测系统运营方；
- 企业内部工程能力评估和晋级考试系统。

### 2.3 用户最终获得什么

一次事故处理最终输出：

1. 经实验确认或明确保留不确定性的根因；
2. 受影响候选人、提交、题目、语言、时间段和批次；
3. 可审批的回滚、隔离、重评与通知方案；
4. 灰度和批量重评进度；
5. 成绩、排名和晋级状态变化；
6. 恢复指标、覆盖率和一致性核验；
7. 可追溯的审批记录与事故报告。

## 三、产品范围与实现边界

### 3.1 核心工程能力

OJGuard 由以下可复用工程能力构成，已完成的能力必须以代码或本地运行证据为准，开发中的能力不得提前写成实测成果：

- FastAPI API、SQLite 持久化和任务状态机；
- C++17 Docker Runner、资源限制和无网络执行；
- 题包导入、规则审计、Checker 审查和确定性主 Demo；
- Finding、Evidence、SHA-256、JSONL Trace 和 HTML 报告；
- 候选补丁、工作副本、回归测试和双重人工确认；
- 标准化 Skill 和受控 MCP 工具；
- AgentTeams Kubernetes 安全部署、独立 TeamLeader 与专业 Worker；
- Vue 3 控制台和自动化测试。

### 3.2 参赛交付范围

- Incident 领域模型和长周期状态机；
- 模拟候选人、提交、监控、部署和投诉数据；
- Java 正常/异常镜像的对照执行能力；
- 多维异常统计、事件关联与根因实验；
- 受影响候选人、提交、成绩和排名计算；
- 控制样例、灰度批次和全量批次的受控重评；
- 临时重评结果、差异计算和模拟成绩写回；
- 新的 Agent、Skill、MCP 工具和事故报告；
- 围绕事故处理主线重构的 Vue 页面。

### 3.3 泛化能力边界

系统不能把业务逻辑写死为“Java 镜像异常”。统一事故模型、Agent 协作流程、状态机、审批、证据和报告必须适用于多类在线测评事故；场景差异通过配置化 Playbook 和受控适配器表达。

交付内容包括：

- 一个完整可运行的 Java 运行环境回归主场景；
- 一个评测节点退化验证场景，用于证明信号切分、根因实验和隔离策略可以复用；
- 一个题包或 Checker 缺陷验证场景，用于证明审计、影响计算和重评流程可以复用；
- 队列拥塞、配置漂移等场景的标准接口和 Playbook Schema，不虚构未实现的执行结果。

泛化来自统一领域模型和稳定扩展点，不要求每种事故复制一套 Agent 或页面。

### 3.4 明确不实现

- 真实企业招聘、短信、邮件或客服系统接入；
- 自动覆盖真实成绩或向候选人发送通知；
- 多租户、生产级账号、真实组织权限和计费系统；
- PostgreSQL、消息队列、对象存储和向量数据库迁移；
- 完整 RAG 知识库；
- 多语言生产级运行环境和所有事故类型的完整执行器；
- 自动作出法律、公平或歧视结论；
- 公网连接真实 OJ 并执行生产操作。

上述能力只保留适配器契约和后续路线，不在界面中展示未启用的端口、模型或技术预留。

## 四、基准主 Demo 与泛化验证

### 4.1 场景

一家企业进行面向 5000 名候选人的后端开发校招测评。14:00，Java 运行镜像从 `java-runtime:v2.3.0` 升级到 `v2.3.1`。升级后 Java 提交的 TLE 率从约 8% 上升到约 42%，C++ 和 Python 基本不变；14:20 起出现多条“同一代码上午通过、下午超时”的投诉。

### 4.2 确定性模拟数据

数据生成器固定随机种子并产生：

- 5000 名脱敏候选人；
- 约 20000 条提交记录；
- Java、C++、Python 的 Verdict 和耗时分布；
- 多个评测节点与队列指标；
- Java 镜像部署变更；
- 20 条客服投诉；
- 题包和 Checker 版本记录；
- 10～20 个控制提交；
- 原始成绩、排名和晋级线。

数据生成规则同时保存期望根因和标准影响范围，保证评测结果可以重新计算。固定种子 `20260802` 的主场景实测影响 703 名候选人、742 条提交，四个控制/灰度/全量批次全部完成，覆盖率 100%，重复、遗漏和越界重评均为 0。

### 4.3 必须跑通的闭环

```text
指标异常 + 提交异常 + 用户投诉 + 部署变更
                    ↓
          聚合信号并创建统一 Incident
                    ↓
       按语言、节点、镜像和时间窗口切分
                    ↓
     同一控制提交在新旧 Java 镜像中重放
                    ↓
         由实验确认或否定根因假设
                    ↓
   计算受影响候选人、提交、成绩与晋级范围
                    ↓
       生成回滚、冻结结果与重评方案
                    ↓
                 人工审批
                    ↓
       控制样例 → 灰度重评 → 分批全量重评
                    ↓
        核验覆盖率、成绩变化和跨语言回归
                    ↓
          二次确认模拟写回并关闭事故
                    ↓
            生成证据化事故报告
```

### 4.4 必须展示的冲突与动态调整

为避免多 Agent 退化为固定流水线，Demo 必须包含一个真实冲突：

- Signal Aggregator 发现异常集中在两个节点；
- Root Cause Analyst 发现异常与 Java 镜像升级同一时间出现；
- Incident Manager 不允许直接投票，而是创建二维对照实验；
- 同一镜像跨节点运行，同一节点跨镜像运行；
- 最终由实验区分“节点故障”和“镜像回归”。

### 4.5 已验证输出

```text
事故状态：RESOLVED

确认根因：
- Java 运行镜像 v2.3.1 的运行参数导致性能回归

影响范围：
- 受影响候选人、提交、时间窗口和招聘批次
- 成绩变化与晋级变化名单

执行动作：
- 生成镜像回滚方案
- 完成控制样例和灰度重评
- 完成受影响提交批量重评
- 生成待人工确认的成绩变更和通知草稿

验证结果：
- Java TLE 率恢复
- 控制提交结果一致
- 重评覆盖率达到 100%
- C++ 与 Python 无新增回归
```

三类场景均由同一脚本重新生成 JSON/HTML 证据；最终材料中的数字只引用 `output/evidence/` 的确定性结果。

### 4.6 泛化验证

除主 Demo 外，自动化测试还要使用同一套 Incident API、状态机和 Agent 编排运行两个小型场景：

| 场景 | 注入异常 | 复用能力 | 验收重点 |
|---|---|---|---|
| 评测节点退化 | 指定节点延迟和错误率升高 | 信号聚合、二维切分、隔离计划、影响计算 | 不将节点问题误判为镜像问题 |
| Checker 缺陷 | 指定题目版本出现误判 | 题包审计、控制用例、影响计算、可信重评 | 不将题目问题扩大到无关题目或语言 |

两个场景用于证明架构泛化，不与主 Demo 争夺展示时间。它们必须产生真实测试结果和证据，不以预设 Agent 文案代替执行。

## 五、总体架构

```text
                    OJGuard Vue 控制台
        事故 / 根因实验 / 影响范围 / 重评 / 审批
                              ↓
                       FastAPI Backend
                              ↓
              Incident 状态机 + 共享上下文
                              ↓
                AgentTeams 业务协作 Team
                              ↓
        Incident Manager / TeamLeader Worker
       ┌────────┬────────┬────────┬────────┬────────┐
       ↓        ↓        ↓        ↓        ↓
   信号聚合   根因分析   影响分析   处置规划   重评执行   独立核验
       └────────┴────────┴────────┴────────┴────────┘
                              ↓
                         Skill Layer
                              ↓
                      OJGuard MCP Server
                              ↓
  数据查询 / 题包审计 / 镜像重放 / 影响计算 / 批量重评 / 报告
                              ↓
          SQLite + Docker Runner + Evidence + Trace
```

### 5.1 泛化架构

核心流程只依赖统一契约：

```text
SignalSource → IncidentProfile → DiagnosticPlaybook
             → ExperimentRunner → ImpactPolicy
             → RemediationAction → VerificationPolicy
             → Evidence / Trace / Report
```

- `SignalSource` 接入监控、提交、部署、题包和投诉信号；
- `IncidentProfile` 描述事故类型、资源范围、时间窗口和严重度；
- `DiagnosticPlaybook` 声明候选假设、所需实验和停止条件；
- `ExperimentRunner` 通过受控工具执行镜像、节点、题包或配置对照实验；
- `ImpactPolicy` 按事故类型计算候选人、提交、成绩和业务范围；
- `RemediationAction` 封装隔离、回滚、重评、冻结和通知草稿；
- `VerificationPolicy` 独立检查恢复指标、覆盖率、一致性和证据完整性。

新增事故类型时优先增加 Playbook 和适配器，不复制状态机、Agent Team、审批页面或报告系统。

### 5.2 推理与执行分离

Agent 只负责：

- 理解异常和业务目标；
- 拆解任务与选择工具；
- 提出可证伪假设；
- 请求对照实验；
- 比较方案和解释结果。

确定性工具负责：

- SQL 查询与统计聚合；
- 新旧镜像执行和重复实验；
- 题包、Checker 和版本完整性检查；
- 影响范围计算；
- 重评批次执行；
- 成绩、排名和覆盖率核验；
- 证据写入、哈希和重放。

### 5.3 技术选型

| 模块 | 实现方案 |
|---|---|
| 多 Agent 协同 | AgentTeams v1.2.0 |
| 前端 | Vue 3 + TypeScript + Vite + Element Plus + Pinia |
| 后端 | Python 3.12 + FastAPI + Pydantic |
| 共享状态 | SQLite；Demo 阶段不迁移 PostgreSQL |
| 工具协议 | OJGuard MCP Server + 明确 JSON Schema |
| 执行环境 | Docker 临时容器，C++17 与 Java |
| 数据 | 固定种子生成的脱敏模拟数据 |
| 证据 | JSON/JSONL/HTML + SHA-256 |
| 模型 | DeepSeek `deepseek-chat`，真实调用受预算控制 |
| 上下文能力 | 共享状态管理 + 轨迹可观测 |

RAG 不是初赛能力，也不是用户功能入口。未来如需接入历史事故和 Runbook，只通过后端 Provider 契约扩展，不在当前产品中展示“预留端口”。

## 六、AgentTeams 与多 Agent 设计

### 6.1 正确的 AgentTeams 映射

AgentTeams 平台 Manager 与 OJGuard 业务 Incident Manager 是两个不同角色：

```text
AgentTeams Platform Manager
└── 创建并管理 OJGuard Incident Team
    ├── Incident Manager：独立 TeamLeader Worker
    ├── Signal Aggregator Worker
    ├── Root Cause Analyst Worker
    ├── Impact Analyst Worker
    ├── Remediation Planner Worker
    ├── Rejudge Executor Worker
    └── Verification & Audit Worker
```

平台 Manager 只负责 Team/Worker 生命周期；业务任务发给 TeamLeader，不能把平台 Manager 写成事故调度 Agent。

### 6.2 Incident Manager / TeamLeader

负责：

- 创建 Incident ID 和结构化共享上下文；
- 根据异常类型拆分和并行派发任务；
- 管理依赖、超时、失败和重试；
- 在 Agent 结论冲突时设计补充实验；
- 控制状态流转与审批节点；
- 汇总最终事故报告。

它无权自行批准批量重评或成绩写回。

### 6.3 Signal Aggregator

聚合提交异常、监控指标、部署变更和投诉，输出统一时间线、异常维度和初步影响信号。不得把时间相关性直接标记为根因。

### 6.4 Root Cause Analyst

提出镜像、节点、配置、题包、Checker 和队列等候选根因，调用确定性工具设计对照实验。每个确认结论至少需要两类独立证据，或一个能够直接复现故障的控制实验。

### 6.5 Impact Analyst

计算受影响候选人、提交、题目、语言、时间段、成绩和晋级状态。只描述技术异常与可计算影响，不作法律或歧视判断；名单导出和业务决策交给人类。

### 6.6 Remediation Planner

生成回滚、隔离、冻结结果、灰度重评、全量重评和通知草稿方案。每个动作必须包含前置条件、验证指标、失败停止条件和回滚点。

### 6.7 Rejudge Executor

只能在审批后执行允许的动作：

- 运行控制提交；
- 小批量灰度重评；
- 根据负载调整并发；
- 分批执行受影响提交；
- 将结果写入临时表；
- 暂停、重试或回滚失败批次。

它不能直接覆盖正式成绩。

### 6.8 Verification & Audit

独立检查：

- 根因实验是否可重复；
- 重评是否覆盖全部受影响提交；
- 是否存在遗漏或重复重评；
- 成绩、排名和晋级变化是否计算正确；
- 是否出现跨语言或跨节点回归；
- 审批和证据是否完整。

输出：`RESOLVED`、`RESOLVED_WITH_WARNING`、`ROLLBACK_REQUIRED` 或 `HUMAN_REVIEW_REQUIRED`。

### 6.9 Agent Identity 交付格式

每个 Agent 都必须按照手册附录生成独立身份卡，并保持配置、代码和方案材料一致：

- Name；
- Role；
- Capabilities；
- Inputs；
- Outputs；
- Dependencies；
- Decision Boundary；
- Trace。

身份卡需要进一步标明允许调用的 Skill、人工介入条件和失败升级路径，避免角色只存在于架构图中。

## 七、共享状态与状态机

### 7.1 IncidentContext

```yaml
incident_id: INC-2026-001
incident_type: runtime_regression
current_stage: INVESTIGATING
profile: {}
resource_scope: {}
playbook_id: runtime-regression-v1
signals: []
active_hypotheses: []
experiments: []
confirmed_root_causes: []
impact_scope: null
remediation_plans: []
approval_state: {}
rejudge_batches: []
score_changes: []
evidence_ids: []
open_questions: []
```

Agent 之间交换结构化对象和证据引用，不复制全部聊天记录作为业务状态。

### 7.2 状态机

```text
DETECTED
→ TRIAGING
→ INVESTIGATING
→ IMPACT_ASSESSING
→ REMEDIATION_PLANNING
→ APPROVAL_PENDING
→ EXECUTING
→ REJUDGING
→ VERIFYING
→ RESOLVED

异常出口：
HUMAN_REVIEW_REQUIRED / PAUSED / ROLLED_BACK / FAILED
```

关键转换必须由确定性条件触发：

- 没有确认根因或明确风险接受，不能进入处置；
- 没有影响范围，不能创建全量重评；
- 没有审批，不能执行高风险动作；
- 控制样例或灰度失败，不能进入全量重评；
- 覆盖率和一致性未通过，不能关闭事故。

## 八、Skill 与 MCP 工具

### 8.1 核心 Skill

| Skill | 作用 | 主要验证方式 |
|---|---|---|
| `normalize-judge-signals` | 归一化告警、提交异常和投诉 | 固定样本聚合结果 |
| `correlate-incident-events` | 关联时间、部署、节点和题包版本 | 时间窗口与控制组 |
| `reproduce-judge-failure` | 跨镜像、节点重放提交 | Docker 实际执行 |
| `audit-problem-package` | 审查题包、Validator、Checker 和数据 | 复用通用题包审计能力 |
| `calculate-impact-scope` | 计算受影响候选人、提交和成绩 | SQL/集合标准答案 |
| `generate-remediation-plan` | 生成处置、验证和回滚方案 | Schema 与策略门禁 |
| `execute-controlled-rejudge` | 执行控制、灰度和批量重评 | 批次记录与幂等检查 |
| `verify-score-consistency` | 核验覆盖率、成绩和排名变化 | 独立重算 |
| `generate-incident-audit-report` | 生成完整事故报告 | 证据引用完整率 |

每个 Skill 必须定义版本、输入、输出、调用条件、错误状态、安全边界、幂等键和验收方法。

1. `incident.list_signals`
2. `submission.aggregate_verdicts`
3. `deployment.list_changes`
4. `judge.replay_submission`
5. `problem.audit_package`
6. `impact.calculate_scope`
7. `rejudge.create_plan`
8. `rejudge.execute_batch`
9. `rejudge.pause_batch`
10. `score.calculate_changes`
11. `verification.verify_incident`
12. `report.generate_incident_report`

每次调用保存工具版本、参数摘要、结果摘要、耗时、错误和 Evidence ID。

## 九、可信重评、审批与回滚

### 9.1 重评不是一键重跑

```text
控制样例验证
→ 小批量灰度重评
→ 指标与结果确认
→ 分批全量重评
→ 覆盖率与一致性检查
→ 二次人工确认
→ 模拟写回正式结果
```

### 9.2 批次保证

- 每个批次使用稳定 `batch_id` 和幂等键；
- 重试不重复写入同一临时结果；
- 记录计划数、完成数、失败数和跳过数；
- 允许暂停、恢复和失败转人工；
- 达到负载阈值时自动降低并发或暂停；
- 任一控制指标恶化时停止后续批次；
- 最终覆盖集合必须等于批准的影响集合。

### 9.3 权限等级

| 等级 | 操作 | 执行策略 |
|---|---|---|
| L0 | 查询、统计、读取证据 | 自动允许 |
| L1 | 沙箱实验、控制样例运行 | 自动允许 |
| L2 | 灰度重评、临时结果计算 | 单次人工批准 |
| L3 | 全量受影响提交重评、冻结结果 | 业务审批 |
| L4 | 正式成绩写回、候选人通知 | 双重审批；MVP 仅模拟 |
| L5 | 删除原始提交或成绩 | 默认禁止 |

参赛团队为一人。演示界面通过“技术负责人”和“业务负责人”两个角色上下文呈现职责分离，由参赛者依次完成确认；系统不得把这一演示机制表述为真实组织中的多人授权。

### 9.4 数据处理边界

- 候选人使用脱敏 ID；
- Agent 只接收完成任务必需的字段；
- 影响名单不发送给模型；
- 正式成绩写回和通知均由模拟适配器实现；
- 原始提交、成绩和题包不被 Agent 直接修改；
- 所有审批、批次和结果变化进入审计记录。

## 十、证据、评测与完成标准

### 10.1 证据类型

- 异常统计和分组查询结果；
- 部署变更与时间线；
- 新旧镜像控制实验；
- 题包与 Checker 哈希；
- 影响范围查询和标准答案；
- 重评计划、批次记录和失败重试；
- 临时成绩、排名差异和晋级变化；
- 审批记录和状态转换；
- Agent/Skill/MCP Trace；
- 最终 JSON 和 HTML 事故报告。

### 10.2 核心指标

| 类别 | 指标 |
|---|---|
| 根因 | 根因识别、假设验证、对照实验重放成功率 |
| 影响 | 受影响提交召回率与准确率、候选人覆盖率 |
| 重评 | 完成率、漏评率、重复重评率、失败恢复率 |
| 结果 | 控制提交一致率、成绩变化重算一致率、跨语言回归数 |
| 审计 | Evidence 完整率、审批记录完整率、报告引用完整率 |
| 效率 | 各阶段耗时、工具调用次数、Agent 调用与模型成本 |

### 10.3 初赛完成定义

只有同时满足以下条件，参赛交付才算完成：

- 模拟数据能够通过固定种子重新生成；
- Java 正常和异常环境确实产生可重复的性能差异；
- 节点退化与 Checker 缺陷场景通过同一 Incident API 和状态机完成验证；
- 新增事故类型不需要复制 Agent Team、审批流程或前端页面；
- AgentTeams 业务 Team 完成一次真实协作；
- 根因由对照实验确认，而不是预设文本直接返回；
- 影响范围与隐藏标准答案一致；
- 控制、灰度和全量重评真实执行；
- 暂停、失败或回滚路径至少验证一条；
- 成绩和晋级变化由程序独立重算；
- 高风险动作不能绕过审批；
- 最终报告能够引用并校验全部关键证据；
- 前端可完成事故查看、审批、重评进度和结果复核；
- 自动化测试、前端构建和密钥扫描通过。

## 十一、前端产品设计

前端只服务用户任务，不展示端口、RAG 预留、模型供应商、Kubernetes、安全自证或比赛架构宣传。

### 11.1 一级入口

1. **工作台**：当前事故、待审批事项和最近结果；
2. **事故**：信号、时间线、根因假设和对照实验；

```text
发生了什么
```

技术 Trace、哈希和工具参数作为详情中的二级信息，默认不抢占主视图。

## 十四、风险与应对

### 14.1 范围失控

Java 镜像回归必须完整运行；节点退化与 Checker 缺陷只验证泛化所需的关键差异路径。任何新增场景都必须复用统一模型和流程，不能以复制代码换取表面功能数量。

### 14.2 企业级故事只有模拟数据

公开数据生成器、异常注入规则、标准答案和查询脚本；所有关键统计和重评真实运行，模拟的是外部系统，不模拟执行结果。

### 14.3 多 Agent 退化为固定流水线

加入节点与镜像冲突假设，由 Incident Manager 动态创建二维对照实验；至少验证一次失败、重试或人工接管。

### 14.4 Java 性能差异不稳定

异常环境使用可解释且可控的资源或运行参数差异，重复多次并报告分布，不依赖一次偶然耗时。

### 14.5 批量重评形成二次事故

固定控制样例、灰度门槛、批次限流、暂停条件、幂等键和临时结果表；失败不得继续扩大范围。

### 14.6 公平性表述越界

系统只计算技术影响、成绩差异和晋级变化，不作法律判断；最终业务与合规决定由人类负责。

### 14.7 模型成本和不稳定性

开发和评测默认使用确定性工具与 Mock；真实 AgentTeams 协作只在集成验收和录制演示时调用 DeepSeek，并遵守剩余 8 元预算和停止门槛。

## 十六、初赛 500 字以内作品简介草案

**OJGuard** 是面向企业招聘考试、在线编程教育和开发者认证平台的多智能体评测事故响应与可信重评系统。线上测评涉及评测节点、语言镜像、题包、Checker、成绩和客服系统；镜像性能回归或题包异常可能直接影响候选人成绩与晋级结果。

OJGuard 基于 AgentTeams 构建独立 Incident Manager 和六个专业 Worker，分别完成信号聚合、根因分析、影响计算、处置规划、重评执行和独立核验。Agent 提出假设，确定性工具通过新旧环境对照实验、数据查询和批量重评验证结论。

所有高风险操作均需人工审批，重评结果先写入临时结果表，覆盖率和成绩一致性通过后才允许模拟写回。主 Demo 聚焦 Java 镜像升级导致 TLE 异常，完整展示异常发现、根因复现、影响计算、灰度重评、成绩变化核验和事故审计；节点退化与 Checker 缺陷测试则验证相同框架能够处理不同信号、假设、实验和影响规则。
