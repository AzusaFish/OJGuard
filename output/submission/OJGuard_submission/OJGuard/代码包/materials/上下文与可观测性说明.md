# OJGuard 上下文与可观测性说明

## 1. 上下文方案选择

OJGuard 当前不把 RAG 声明为已实现能力。项目按赛题的非 RAG 路径实现以下两项核心上下文能力，并提供第三项辅助能力：

| 能力 | 实现 | 作用 | 证据 |
|---|---|---|---|
| 共享状态管理 | SQLite 中的结构化 `IncidentContext`、`AgentRun`、审批、计划版本、批次、成绩变化和证据索引 | 保证 Agent 读取同一业务事实，支持恢复、门禁、集合比较、执行预算和最终核验 | `backend/app/services/repository.py`、三类事故 JSON 报告 |
| 轨迹可观测 | 顺序化 `AgentRunEvent` 持久化 `ROUTE_DECISION`、`WORKER_RESULT`、工具、前后状态、证据引用、人工门禁、暂停/恢复和最终报告；AgentTeams Matrix 事件 ID 用作幂等键 | 证明 Team Leader 从 `TRIAGING` 开始逐步路由，避免重复计数，并支持进程外查询与回放 | `/api/v1/agent-runs/{run_id}/events`、`/stream`、`output/evidence/agentteams/agentteams-demo-result.json` |
| Agent 历史记忆（辅助） | AgentTeams Matrix 房间历史与导出的脱敏事件 | 支持 Team Leader 汇总 Worker 结果；业务真相仍以共享状态和 Evidence ID 为准 | AgentTeams 实机证据和导出脚本 |

因此，未启用知识库 RAG 不影响上下文闭环。未来知识检索只能作为新的 Provider 和 Skill 数据源接入，不能替代状态机、审批、工具证据或独立核验。

## 2. 观测数据模型

| 类型 | 采集内容 | 存储 | 检索/使用方式 |
|---|---|---|---|
| Trace | `run_id`、`task_id`、`incident_id`、递增 `sequence`、Agent/Worker、action、tool、前后阶段、Evidence ID、事件类型和最终状态 | SQLite `orchestration_runs` / `orchestration_events`；AgentTeams 脱敏 JSON作为可移交证据 | 按运行或事故查询；`after_sequence` 增量读取；SSE 订阅；用 Matrix 事件 ID 幂等去重 |
| Log | MCP 安全错误、后端请求、Runner 结果、批次状态、报告生成结果 | 运行期日志、SQLite 领域记录、JSON/HTML 报告 | 定位工具失败、审批缺失、灰度停止和人工接管原因 |
| Metrics | 基线/观测失败率、控制实验通过率、影响数量、批次完成/失败/跳过数、覆盖率、重复/遗漏/越界数、Worker 返回数 | 事故 JSON 报告、Java 对照证据、AgentTeams 结果 | 演示后定量核验根因、影响、执行正确性和协作完整性 |

当前采用 OJGuard 内部稳定字段，不宣称已接入 OpenTelemetry GenAI 语义规范或专用可观测平台。若迁移到 OpenTelemetry，应保持 `task_id`、`incident_id`、Agent、Skill、MCP 工具、Evidence ID、阶段、耗时、结果和错误码字段，并映射为 span/resource attributes；现有 JSON/SQLite 证据仍可作为对照标准答案。

## 3. 全链路关联

```text
用户/告警输入
  → IncidentContext 创建
  → Team Leader 任务拆解
  → Worker + Skill
  → MCP 工具调用
  → Evidence ID / 指标 / 批次记录
  → 人工审批或失败出口
  → 独立 Verification
  → JSON/HTML 事故报告
```

关联规则：

- `incident_id` 是业务主关联键；AgentTeams 实机演练额外使用 `task_id`。
- 每次协作执行使用独立 `run_id`，事件按 `sequence` 严格递增；相同事件 ID 重放只返回原记录，不增加模型响应计数。
- Agent 之间传递 Evidence ID、集合哈希和结构化对象，不依赖未经验证的自然语言记忆。
- 每次状态变化都必须满足确定性状态机条件；高风险动作还必须存在持久化审批。
- 最终验证从批次和快照独立重算，不直接信任 Rejudge Executor 的总结。
- 报告只引用已经持久化的根因、影响、审批、批次、成绩变化和验证结果。

## 4. 效果证明

- Java 运行时回归：正常环境 3/3 OK、退化环境 3/3 TLE，控制实验可重复率 100%。
- 主场景：703 名候选人、742 条提交；控制、灰度和全量共 742/742 完成。
- 独立验证：覆盖率 100%，重复、遗漏和越界均为 0。
- 多 Agent：Team Leader 在每个状态读取上下文并选择下一 Worker；六个 Worker 分阶段写回结果，技术/业务/关闭门禁由人工完成，事故关闭后才统一汇总。
- 动态性与恢复：节点场景公开 3 个实验候选；确定性证据先选择一个 `INCONCLUSIVE` 实验，再改选能够区分假设的实验；灰度失败后暂停、计划升级至 revision 2、撤销并重做技术审批、恢复灰度通过。
- 失败恢复证据：覆盖率 100%，重复、遗漏、越界均为 0；文件明确记录 `model_calls=0` 和 `paid_api_cost=0`，与真实 AgentTeams 调用证据分开。
- 泛化场景：节点退化和 Checker 缺陷复用同一 IncidentContext、Skill、状态机、审批和报告链路。

## 5. 数据边界

- 场景数据为固定种子生成的脱敏模拟数据，不连接真实候选人、成绩库或生产 OJ。
- 运行证据不保存 API Key、登录令牌或未脱敏个人信息。
- `.env`、运行数据库、缓存、依赖目录和 AgentTeams 登录状态均从最终 ZIP 排除。
- 前端只展示事故处置所需业务信息，不展示 RAG 端口、模型供应商或内部基础设施配置。
